# 综合项目 · 校园活动服务平台（管理端）

课程综合项目。业务主线是“活动发布 → 报名审核 → 场次安排”，前端实现 5 个业务页面 + 1 个登录入口 + 1 个数据看板。

选这个载体是因为学生本身就是场景的真实用户，需求不用额外解释，同时它天然带着状态流转、时段冲突、名额联动、角色区分这些可教可练的点。

## 功能范围

| 模块 | 功能点 | 验收要点 |
| --- | --- | --- |
| 登录与鉴权 | 账号密码登录、记住登录状态、退出登录、未登录拦截；按角色区分可见菜单 | 刷新页面登录态不丢；受限页面无法直接访问；换角色登录后菜单随之变化 |
| 活动管理 | 活动列表（关键词搜索 / 分页 / 状态筛选）、新建、编辑、详情、下架 | 四态齐全；表单校验完整；多个筛选条件可组合，结果与条件一致 |
| 报名审核 | 报名名单列表、按活动与审核状态筛选、通过 / 驳回（驳回必填理由）、批量处理 | 状态流转正确；批量操作有二次确认；操作后台账数据同步更新 |
| 场次与场地 | 场次列表、新增场次、选择场地与时段、冲突提示、名额与已报名人数联动 | 冲突检测即时提示且不误报；名额与已报名数联动正确 |
| 数据看板 | 指标卡片（活动数 / 报名人数 / 待审核数 / 签到率）、近七日报名趋势、待办清单 | 数据来自接口；加载与异常状态有处理；点击待办能跳到对应列表 |

## 业务规则

| 规则 | 前端要处理的事 |
| --- | --- |
| 活动状态流转：草稿 → 报名中 → 报名截止 → 已结束；下架是独立标记，下架后任何入口都不可见 | 列表与详情的操作按钮随状态变化；非法流转的操作直接不出现 |
| 名额与报名数联动：已通过人数达上限时报名入口关闭，有人取消则重新开放 | 用派生状态算，不另存字段 |
| 时段与场地不冲突：同一场地同一时段只能有一场活动，起止区间重叠才算冲突 | 选定后立刻提示；判断抽成纯函数，便于补单元测试 |

两个角色：活动组织者负责新建活动、配置场次与场地、查看报名、导出名单；审核员只处理报名审核与签到台账。角色差异要同时落在菜单、路由与按钮三处。

## 三阶段交付

| 阶段 | 周次 | 交付内容 | 验收标准 |
| --- | --- | --- | --- |
| 第一阶段 | 第 9-10 周 | 路由与状态骨架、登录鉴权闭环、请求层封装 | 未登录访问受限页面被拦下并在登录后回到原地址；接口错误有统一提示 |
| 第二阶段 | 第 11 周 | 需求规格说明、活动列表 / 活动编辑 / 报名审核三个核心页面 | 用真实接口能完成一次完整的“登录 → 查询 → 新增 → 修改 → 删除” |
| 第三阶段 | 第 12 周 | 数据看板、构建优化、服务器部署、交付文档与答辩 | 公网地址可访问；交付文档含接口对照与已知问题；答辩能讲清技术决策 |

## 技术要求

| 要求 | 说明 |
| --- | --- |
| 统一使用组合式 API | 全部组件用 `<script setup>` |
| 组件化拆分 | 单个组件文件不超过 300 行，基础组件与业务组件分目录 |
| 状态与数据分层 | 接口地址不在组件里硬编码；全局状态只在确实跨页面共享时使用 |
| 异常处理 | 所有异步请求都有加载态与错误态 |
| 代码规范 | 提交前通过检查与格式化，提交信息符合规范 |
| 可交付 | 仓库根目录有说明文档，他人按文档能在 15 分钟内跑起来 |

## 分层要求

| 层次 | 内容 |
| --- | --- |
| 基础层（必做） | 登录鉴权 + 活动管理模块（列表与表单）+ 四态处理 + 部署上线 |
| 进阶层（选做） | 报名审核与场次场地模块、数据看板、列表页通用组件抽取 |
| 挑战层（加分） | 按钮级权限控制、冲突检测抽成独立 composable 并补单元测试、导出报名名单、列表列配置持久化 |

## 跑起来

```bash
pnpm install
pnpm dev
```

联调前确认后端服务已启动，代理规则见 `vite.config.js`。
